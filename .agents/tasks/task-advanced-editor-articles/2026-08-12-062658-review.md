# TipTap rich-text editor and articles CRUD for city/state/service pages

This change replaces the plain markdown textarea in the blog post editor with a WYSIWYG TipTap editor, and adds a full admin section for managing `blog_articles` (city/state/service page content) with the same rich editor and a side-by-side live preview. The approach wraps TipTap with the `tiptap-markdown` bridge so the editor outputs markdown that feeds directly into the existing `markdownToBlocks` → `ArticleBlocks` rendering pipeline. The articles admin mirrors the blog admin pattern: listing page with type filter, editor page with metadata fields + content editor + live preview.

Watch for: H2 headings created in the editor will silently render as H3 on the published page due to a mismatch between TipTap's markdown output (`##`) and the parser's regex that expects single `#` for H2 (confirmed). The editor toolbar is limited (no color, highlight, underline, strikethrough, code block, or image support) relative to what was requested as a "fully advanced editor" (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The RichMarkdownEditor component configures TipTap with StarterKit, Link, Table, and the tiptap-markdown bridge. The toolbar exposes bold, italic, H2, H3, bullet/ordered lists, blockquote, table, link, and horizontal rule. This covers basic formatting but falls short of the user's request for colors and "all the options available in a fully advanced editor" — there's no text-color extension, highlight, underline, strikethrough, code block, image upload, or font-size control.

The markdown-to-blocks pipeline has a heading-level compatibility gap. The parser maps single `#` to `{ h }` (H2) and `##`/`###` to `{ sub }` (H3). TipTap's StarterKit configured with `levels: [2, 3]` emits `##` for H2 and `###` for H3 — so both heading levels from the editor collapse to H3 in the preview and on published pages.

The articles admin is a CRUD pair (listing + editor) for the `blog_articles` table. The editor page has a two-column layout: metadata form + rich editor on the left, live preview rendered through the real ArticleBlocks pipeline on the right. Slug fields (city_slug, area_slug, service_slug) lack conditional validation per page_type, allowing orphaned articles that can't be associated with any page.

## Heading level mismatch between TipTap output and markdownToBlocks parser

The editor is configured with `heading: { levels: [2, 3] }`, meaning the lowest heading a user can insert is H2. TipTap's markdown serializer outputs H2 as `## Heading` (two hashes) and H3 as `### Heading`. The `markdownToBlocks` parser in `src/utils/markdownToBlocks.js` uses this logic:

```js
// H2 heading: # Heading
if (/^#{1}\s+(.+)$/.test(trimmed)) { ... blocks.push({ h: match[1] }) }

// H3 subheading: ## or ### Subheading
if (/^#{2,3}\s+(.+)$/.test(trimmed)) { ... blocks.push({ sub: match[1] }) }
```

A single `#` maps to `{ h }` (rendered as H2 by ArticleBlocks). Two or three hashes both map to `{ sub }` (rendered as H3). Since TipTap never produces single-hash headings (its configured minimum is `level: 2` = `##`), every H2 the user creates in the editor will be demoted to H3 in the live preview and published page. The preview panel sits right next to the editor, so this mismatch will be immediately visible and confusing.

Fix: change `markdownToBlocks` to treat `##` as `{ h }` and `###` as `{ sub }`, moving the single-`#` case to map to an even larger heading or removing it. Alternatively, add `level: 1` to the editor's heading config so it emits `#` — but that's semantically wrong for article subheadings. Confidence: **confirmed**.

## Editor toolbar gaps relative to user requirements

The user's request specified "colors, Bold & all the options available in a fully advanced editor." The current toolbar provides: Bold, Italic, H2, H3, Bullet List, Ordered List, Blockquote, Table, Link, Horizontal Rule. Missing:

- Text color / highlight (needs `@tiptap/extension-color`, `@tiptap/extension-text-style`, `@tiptap/extension-highlight`)
- Underline (`@tiptap/extension-underline`)
- Strikethrough (in StarterKit but not exposed in toolbar)
- Code / code block (in StarterKit but not in toolbar)
- Image insertion (`@tiptap/extension-image`)
- Font size / font family
- Text alignment (`@tiptap/extension-text-align`)

Note that adding color/highlight extensions creates a secondary concern: the `tiptap-markdown` bridge and `markdownToBlocks` parser have no way to represent colored text in markdown. These features would require switching the storage format to HTML or a custom JSON structure for affected blocks, which is a larger architectural decision. Confidence: **confirmed**.

## Slug fields lack conditional validation

AdminArticleEditor validates only that the title is non-empty before saving (`handleSave` line ~85). The slug fields (`city_slug`, `area_slug`, `service_slug`) are all optional regardless of `page_type`. For page_type `'city'`, an empty `city_slug` means the article can't be matched to any city page during rendering. The listing page shows these as `-` with no warning. Confidence: **confirmed**.
