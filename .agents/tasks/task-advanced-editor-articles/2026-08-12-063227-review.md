# TipTap WYSIWYG editor with articles CRUD and v1 fix pass

This change adds a TipTap-based rich-text editor to the blog admin and introduces a complete articles CRUD section for managing city/coworking/service page content. The editor outputs markdown via the `tiptap-markdown` bridge, feeding into the existing `markdownToBlocks` → `ArticleBlocks` rendering pipeline. A fix commit resolves all four issues from the v1 review: heading-level mismatch in the parser, missing toolbar buttons (strikethrough, inline code, code block), editor lifecycle cleanup (`immediatelyRender: false`), and slug validation per page_type.

Watch for: The editor still doesn't include text color, highlight, underline, image upload, or text-align — features the user explicitly requested as part of a "fully advanced editor" (confirmed). The markdown storage format makes adding color/highlight structurally difficult without an architectural change. No automated tests exist for the `markdownToBlocks` parser (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

All four v1 issues are resolved. The parser now checks `###` before `#{1,2}`, correctly mapping `##` → `{ h }` (H2) and `###` → `{ sub }` (H3), which aligns with TipTap's output. The toolbar gained strikethrough, inline code, and code block buttons. The editor passes `immediatelyRender: false`. The article editor validates city_slug for city/coworking types and service_slug for service type before saving.

The gap between what was delivered and what was requested remains the primary concern. The user asked for "colors, Bold & all the options available in a fully advanced editor." The toolbar covers structural formatting well (headings, lists, quotes, tables, code) but omits visual formatting (text color, highlight, underline, text-align) and media (image insertion). These omissions are partly an architectural constraint — markdown cannot represent colored text — and partly missing extensions that would work fine (underline, text-align via HTML storage).

The `markdownToBlocks` parser has no test coverage. Given the subtle ordering sensitivity of its regex checks (the v1 heading bug was exactly this class of problem), the parser is fragile against future changes.

## Editor feature gap relative to "fully advanced editor" request

The user's instruction was: "Can we make it more advanced editor type for eg, colors, Bold & all the options available in a fully advanced editor?" The current toolbar covers:

- Text: Bold, Italic, Strikethrough, Inline Code
- Structure: H2, H3, Bullet List, Ordered List, Blockquote, Code Block, Table, HR
- Inline: Link

Missing from the request:

- Text color / background highlight — requires `@tiptap/extension-color`, `@tiptap/extension-text-style`, `@tiptap/extension-highlight`
- Underline — `@tiptap/extension-underline`
- Image insertion — `@tiptap/extension-image`
- Text alignment — `@tiptap/extension-text-align`
- Font size/family

The fundamental constraint is the storage format. The `tiptap-markdown` bridge serializes to markdown, which has no representation for colored text, highlighted text, or aligned paragraphs. Adding these features requires either switching content storage to HTML (which `markdownToBlocks` can't parse) or creating a hybrid format. This is an architectural decision that should be made explicitly rather than discovered when someone adds a color extension and finds it doesn't persist.

## Parser fragility without tests

The `markdownToBlocks` function processes lines sequentially with regex matches. The order of checks matters: `###` must be tested before `#{1,2}` to avoid the longer pattern consuming three-hash headings as two-hash matches. The v1 review caught exactly this bug.

The parser has no test coverage. A single unit test file covering the heading-level mapping, bullet list flushing at paragraph boundaries, multi-line quote accumulation, and table parsing would prevent regression. Given this parser is the rendering backbone for all article content, the risk of a future regex-ordering mistake breaking published pages is real.

## Link protocol validation

```jsx
function setLink() {
  const prev = editor.getAttributes('link').href
  const url = window.prompt('URL', prev || 'https://')
  // ...
  editor.chain().focus().extendMarkRange('link').setLink({ href: url }).run()
}
```

The URL from `window.prompt` is passed directly to TipTap without protocol validation. TipTap's Link extension v3 includes built-in `validate` logic that rejects `javascript:` protocols by default, but the code relies on library defaults without explicit configuration. A one-line defense-in-depth addition:

```js
Link.configure({
  openOnClick: false,
  validate: href => /^https?:\/\//.test(href),
  HTMLAttributes: { class: 'text-blue-600 underline' },
})
```
