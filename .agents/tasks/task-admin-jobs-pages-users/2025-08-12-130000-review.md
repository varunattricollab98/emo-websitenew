# Admin panel expansion: jobs CRUD, editable site pages, user management, unified nav

This change adds four features to the admin panel: a jobs/vacancies CRUD system, a site-pages editor that lets admins override hardcoded legal page content via Supabase, a user management system with role-based access control (admin vs editor), and a shared AdminNav component that unifies navigation across all admin sections. The approach follows the existing pattern of storing the Supabase `service_role` key in sessionStorage and using it client-side for all write operations.

Watch for: Plaintext password storage in the database with no hashing (confirmed). The credential comparison and fallback auth bypass also allow login with hardcoded credentials even when the database table exists. Role enforcement is purely client-side — any user with the service key can bypass role restrictions via direct Supabase calls.

**Verdict**: NEEDS_CHANGES

## High-level view

Authentication and password management is the blocking concern. Passwords are stored and compared as plaintext strings — the SQL seed inserts `'emo@2026'` directly, and `AdminLogin.jsx` compares `user.password !== password.trim()`. This means anyone with database read access (or a backup leak) gets every admin credential in the clear. Additionally, the hardcoded fallback credentials remain active even when the `admin_users` table exists and responds successfully, because `fallbackAuth()` is the catch-all for any network error.

Role-based access control is cosmetic. The `adminOnly` flag in AdminNav and the `role !== 'admin'` redirects in listing pages only hide UI elements. Since the admin client uses the `service_role` key (which bypasses RLS entirely), an editor who opens devtools can hit any table directly. The RLS policy on `admin_users` restricts access to `service_role` only, which is moot because every admin session already holds that key.

Each legal page fetches its slug from `site_pages`, renders markdown via `ArticleBlocks` if content exists, and falls back to the original hardcoded sections. The `LegalLayout` was extended with a `children` prop to support injected content without breaking existing section rendering.

The AdminNav component centralizes link definitions and logout, replacing per-page nav boilerplate in listing pages. The editor pages (AdminJobEditor, AdminPageEditor, AdminUserEditor) still carry their own logout buttons and back-links rather than using AdminNav, creating a maintenance split.

## Plaintext credential storage and comparison

The `admin_users` schema defines `password text NOT NULL` with no constraint or transformation. The SQL seed inserts the literal string `'emo@2026'`. In `AdminLogin.jsx`, the authentication path fetches the row and compares:

```js
if (user.password !== password.trim()) {
  return { success: false, error: 'Invalid username or password.' }
}
```

This is a direct string equality check against the stored cleartext value. The `AdminUserEditor` stores new passwords the same way — `payload.password = form.password.trim()` goes straight into an `insert` or `update` call. Any database export, log, or RLS misconfiguration exposes every credential.

The fix is to hash passwords before storage (bcrypt via a Supabase Edge Function or a migration to Supabase Auth) and compare hashes during login. The current architecture makes this awkward since all logic runs client-side, but a Supabase RPC function could handle the comparison server-side.

## Fallback auth bypass remains permanently reachable

`AdminLogin.authenticateUser` calls `fallbackAuth()` whenever the Supabase query throws (the `catch` block), or when the error message matches certain patterns indicating the table doesn't exist. The intent is graceful degradation before the table is created. However, the `catch` block is unconditional:

```js
} catch {
  // Network error or table doesn't exist - fall back
  return fallbackAuth()
}
```

A transient network failure, a Supabase outage, or a CORS error will trigger `fallbackAuth()`, which accepts `admin`/`emo@2026`. This means the hardcoded credentials remain a permanent backdoor regardless of what's in the database. The safe pattern is: only invoke the fallback when the specific error code is `42P01` (relation does not exist); for all other errors, fail closed.

## Role enforcement is UI-only

AdminJobs, AdminPages, and AdminUsers check `sessionStorage.getItem('admin_role')` and redirect editors away. AdminNav hides the "Users" link for non-admins. But since every logged-in user holds the `service_role` key in sessionStorage — the key that bypasses all RLS — any editor can call `getAdminClient().from('admin_users').select('*')` from the browser console and read/write everything.

The RLS policy on `admin_users` is:

```sql
CREATE POLICY "Service role full access" ON admin_users
  FOR ALL
  USING (auth.role() = 'service_role')
  WITH CHECK (auth.role() = 'service_role');
```

This explicitly grants the service role (which every admin session uses) full access. For real role separation, the admin panel would need either: (a) per-user Supabase Auth tokens with RLS policies that check the user's role claim, or (b) an Edge Function that validates the caller's role before proxying writes.

## Password field rendered as visible text

In `AdminUserEditor.jsx`:

```jsx
<input
  id="user-password"
  type="text"
  value={form.password}
  ...
/>
```

The `type="text"` makes the password visible to shoulder-surfers and may prevent password managers from treating it correctly. This should be `type="password"`.

## No guard against self-deletion

`AdminUsers.handleDelete` confirms with a dialog but does not check whether `id` matches the currently logged-in user. An admin can delete themselves, losing access to the system with no recovery path (since the only way to re-create users is through the admin panel itself).

## Editor pages don't use AdminNav

`AdminJobEditor`, `AdminPageEditor`, and `AdminUserEditor` each implement their own back-link and logout button rather than rendering the shared `AdminNav` component. This means navigation changes need to be updated in four places instead of one.
