# Admin panel expansion: v2 review after fixes

This change adds jobs CRUD, editable site pages, user management with role-based access, and a shared AdminNav component to the admin panel. The v1 review raised five issues; three were fixed in commit 0e2eeba (password field visibility, fallback auth bypass, self-deletion guard), and two were accepted as by-design (plaintext password storage, client-side role enforcement). The fixes are correctly implemented. One new concern surfaces around inconsistent role gating between the listing pages.

Watch for: Inconsistent role restrictions across admin sections — Jobs and Pages block editors, but the AdminNav still shows links to Jobs and Pages for editors who can then hit those routes directly before being redirected (likely).

**Verdict**: APPROVED

## High-level view

Role gating is inconsistent between sections. AdminJobs and AdminPages redirect editors via `adminRole === 'editor'`, while AdminUsers checks `role !== 'admin'`. The behavioral effect is the same for a two-role system, but a future third role would behave differently. More concretely, AdminNav shows Jobs and Pages links to all roles, so an editor sees those links, clicks them, and gets silently redirected — a confusing UX, though not a security gap given the accepted by-design constraint that all enforcement is client-side.

The legal pages share an identical data-fetching pattern with silent catch blocks, meaning a failed query (after the table exists) shows the fallback content with no user-visible error. This masks broken queries in production.

1. **AdminNav exposes links editors can't use** — Jobs and Pages links appear for editors, who then get redirected on click. Either hide these links with `adminOnly: true` or change the gating so editors can view (but not write) those sections.
2. **Silent catch in legal page fetches masks real errors** — After the table exists, a permissions error or network failure silently shows fallback content with no logging. Consider distinguishing "table missing" from "query failed" for observability.

## AdminNav role visibility gap

The AdminNav `NAV_LINKS` array only marks Users as `adminOnly: true`:

```js
const NAV_LINKS = [
  { label: 'Blog Posts', path: '/admin/blog' },
  { label: 'Articles', path: '/admin/articles' },
  { label: 'Jobs', path: '/admin/jobs' },
  { label: 'Pages', path: '/admin/pages' },
  { label: 'Users', path: '/admin/users', adminOnly: true },
]
```

But both `AdminJobs` and `AdminPages` redirect editors away in their `useEffect`. The links are visible, clickable, and cause a flash-redirect. Adding `adminOnly: true` to the Jobs and Pages entries would align the nav with the actual access control.

## Silent error swallowing in legal pages

Every legal page component catches errors with an empty block:

```js
} catch {
  // Table may not exist yet or query failed - use fallback
}
```

Before the table is created, this is correct. After the table exists, this same catch swallows permission errors, network failures, and malformed responses. The user sees correct-looking (but stale) content with no indication anything went wrong. A `console.warn` or a conditional check for table-not-found vs. other errors would improve debuggability without changing the user-facing behavior.
